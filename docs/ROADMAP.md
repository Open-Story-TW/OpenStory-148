# 實作路線、容量驗收與遷移

## 需求與完成定義

容量目標：使用者指定 **5,000 總 CCU**。預設壓測兩個世界各 2,500 人、每世界 11 個可配置頻道；另測單世界 5,000 人及負載集中情境。這是設計／驗收目標，還沒有實測結果。

| ID | 需求 | 驗收位置 |
| --- | --- | --- |
| R01 | Go 重寫並相容現有 TMS 145.1／OpenMaple | P0、P2–P5 實機與 golden packet |
| R02 | PostgreSQL + Ent + 版本化 migration | P1 與 P7 匯入核對 |
| R03 | Redis 快取、登入避免逐隻完整載入 | P2 查詢預算、P6 冷／熱 cache |
| R04 | login／cashshop／每 world 獨立程序，多頻道 | P1 程序啟停、P4 跨程序流程、P6 kill test |
| R05 | 5,000 CCU，指定環境與負載組合 | P6 容量報告 |
| R06 | 單一寫入者、交易冪等、無複製道具 | P1 fencing、P3／P4 競態、P6 故障注入 |
| R07 | 保留玩家資料／內容相容與可核對遷移 | P0 全表盤點、P5 覆蓋矩陣、P7 |
| R08 | 監控、備份、故障恢復與獨立部署 | P1 基礎、P6／P7 演練 |

## P0：鎖定基線與協定契約

交付：Java／SQL／WZ／OpenMaple receipt 的版本與 checksum；全部舊表欄位的轉換處置；opcode／packet shape、字串編碼、IV 與數字範圍 fixture；核心流程 query count／latency 基線。

工作：

- 對照 Java `addCharStats`／`addCharLook`，列出 roster DTO 的完整欄位及 byte layout。
- 驗證 v145 的登入／選角／跨程序重連憑證承載；必要時設計 OpenMaple 的有版本擴充，先解決一次性交接安全性。
- 收集多種角色大小：空角色、滿背包、多任務／技能、寵物、商城倉；測 N+1、全量存檔與資料量，不把結構推論當成測得的瓶頸。
- 列出 Nashorn Java 互通與 `cm`／`em`／其他腳本 API；盤點事件、任務與職業覆蓋，辨識舊包已缺的資源。

通過條件：fixture 可重播、每個封包欄位來源可追蹤；legacy table／column 無未標記處置；安全交接方案完成 PoC。這階段不宣告整個 Java 功能已移植。

## P1：多程序基礎與持久化

交付：Go module／版本鎖定、四個可獨立啟動的服務、配置、PG／Redis 隔離開發環境、核心 Ent schema 與 migration、RPC 身分與期限、監控、runtime lease／session generation、outbox。

開發資料庫使用新 database／port，來源 MariaDB 可讀快照；Go 測試帳號與客戶端也使用隔離配置。版本選當時支援的穩定版並固定 patch／image digest；PostgreSQL 初始以 18 系列驗證，最終仍由實作時的相容矩陣鎖定。

通過條件：每個 binary PID 獨立；單獨終止不會呼叫全域退出其他服務；過期 epoch 的寫入被拒；migration 可在空庫與上一版執行；失敗提交不改資產；連線預算與設定驗證有效。

## P2：登入、角色摘要與創角

交付：v145 crypto／framing、帳號／第二密碼、世界／頻道目錄、roster Redis cache、創角與刪角狀態、所選世界的 CreateCharacter RPC。

通過條件：實際客戶端登入到角色列表／創角；60 個角色槽或已確認的客戶端上限下，cache miss 仍是 1–2 次摘要 SQL；列表不讀 quest／skills／完整 inventory；cache hit 不做角色詳細 SQL。帳密／授權 SQL 仍會執行。新角色權限與庫存約束正確，Redis 清空仍可登入。

## P3：世界、頻道、地圖與保存

交付：世界／頻道設定、玩家單一寫入者、核心地圖／NPC／移動／打怪、道具／楓幣 ledger、任務與技能基礎、增量 checkpoint、斷線與獨立正常關機。

通過條件：實機創角 → 進圖 → 移動／戰鬥／拾取 → 保存 → 重啟；PG 不做 per-movement 讀取；同時拾取／重送不發重複物品；新 checkpoint 不被舊保存覆寫。角色讀取的 SQL budget 不隨任務列數變成 N+1。

## P4：同世界換頻與跨程序商城

交付：session generation、短效交接、世界內記憶體換頻、商城購買／點倉／交付與返回世界、限量／退回／失敗處理。

通過條件：實機 world 0 ch1 → ch2 → cashshop → world 0；每個交接只能消費一次；錢與物品在重送／逾時／雙登入下守恆；world 0 終止時 world 1 與商城仍工作，商城訂單不需要存活的 world 才能核對。原世界不可用時可留商城或返回登入，不強行連入無效世界。

## P5：功能與內容覆蓋

先建立清單再逐項實作／驗收：各職業技能／Buff／冷卻、裝備／強化／潛能、寵物、任務、NPC／活動腳本、公會／好友／隊伍、交易／倉庫／商店、副本／Boss、商城完整操作、GM／後台與自訂功能。

每項標記 `Java 行為`、`Go 支援`、`實機案例`、`資料轉換`、`已知差異`。優先交付可玩的垂直流程，但在未覆蓋的職業／內容仍存在時，不能宣告「完整重寫完成」。腳本的 Java API 互通需用 Go facade／資料化規則或逐支改寫取代，不會隨 JS VM 自動相容。

通過條件：目標開放內容均有正向／拒絕／存檔／重啟案例；未上線內容可配置關閉且玩家資料仍被保留；WZ manifest 與客戶端相容性核對完成。

## P6：5,000 CCU 與故障驗收

測試要記錄 CPU 型號、核心、RAM、磁碟／IOPS、網路、OS、DB／Redis 設定、資料分布、build hash 與隨機種子。資源初估只用於建立實驗，不能作為已達標的硬體保證。

| 情境 | 負載 |
| --- | --- |
| 總容量 | 兩世界各 2,500，頻道與地圖不均勻分布，逐步升載到 5,000 |
| 單世界 | 一個 world 承載 5,000；觀察 CPU／heap／tick／網路，確認每世界容量界限 |
| 活躍玩家 | 約 60% 移動／戰鬥，20% NPC／背包／任務，10% 換頻／商城，10% idle；各動作頻率另記錄，不把 5,000 個閒置 socket 當達標 |
| 熱門地圖 | 同圖 200／500／1,000 逐步測試，含怪物、AOI、技能廣播；找出可支援上限與超限行為 |
| 大角色 | 滿背包、多任務／技能、商城物品與中文名稱；不能只用空角色 |
| 登入尖峰 | 分別 50／100／200 login attempts/s，分開計成功登入與受控 busy／限流；測 hash 工作池 |
| 保存尖峰 | 5,000 個角色皆 dirty，checkpoint／資產命令混合，測排程抖動與 WAL |
| 冷 cache | 全部 cache miss／Redis 離線，登入與角色列表受控回源，現有在線玩家持續 |
| 穩定性 | 5,000 CCU 至少 8 小時，並以較長 24 小時 soak 觀察 heap／goroutine／pool 漏洩 |

初始服務端目標（待 profile 調整並公開調整理由）：

- 角色列表：cache hit P95 ≤50 ms、cold P95 ≤200 ms，從 handler 開始至回覆，排除帳密驗證與外網。
- 正常進圖／換頻：端到端 P95 ≤2 秒；以實機樣本與負載客戶端分別報告。
- 地圖工作／命令排隊：P99 ≤50 ms；高頻處理時間與 durable economic command latency 分開統計。
- 正常資產提交：P99 ≤200 ms；過載有受控 busy，不能無界排隊。
- 核心程序 CPU 持續負載保留約 30% headroom；記憶體與 queue 不持續增長。實際上限由指定硬體測試得出。
- 一般保存 lag／回檔目標 ≤10 秒；已確認資產在程序 crash 後不遺失、不重複。

故障注入：逐個 kill login／cashshop／world／worker、world OOM、Redis 清空／斷網、PG 連線耗盡／延遲、commit 回覆丟失、world 舊程序暫停後恢復、交接中重送／斷線、DB primary failover、服務冷啟動湧入。記錄存活服務是否繼續、實際 RPO／RTO 與資產對帳。world 重啟含租約等候的初始 RTO 目標 ≤60 秒，需實測。

負載產生器重播合法狀態機，不用直接呼叫內部函式代替 socket；少量真實圖形客戶端驗證畫面、協定和實際玩法。最終容量報告附原始測試輸出與未通過情境。

## P7：遷移、切換與回復

1. 對來源 schema／資料做快照與 checksum；只讀匯入新的 PG 庫，保留來源 ID 與未知欄位封存。
2. 核對每表 row count、角色等級／金額和、物品唯一性與歸屬、任務／技能數、帳號與名稱衝突、外鍵孤兒、時區／到期；抽樣實機登入。
3. 用同一來源快照做至少兩次可重複匯入演練；驗證序列下一號與新建角色不碰撞。
4. 正式切換先維護、停止 Java 寫入、保存玩家、取得最後一致快照，再匯入與對帳。Java／Go 不同時寫同一份玩家資料；早期階段也不做無界雙寫。
5. 上線前演練 PG 備份還原／WAL 恢復，測讀檔與 ledger。切換完成後 Redis 由空庫重建。
6. **PG 接受 Go 新寫入前**可直接切回凍結 Java；**接受新寫入後**回 Java 需要已驗證的反向轉換／增量重播並停寫對帳。沒有反向工具時採修復 Go／恢復 PG，不把開回舊 Java 說成無損回復。

## 實作前仍需收斂的項目

- 5,000 CCU 已確定；世界數初始採兩個，另有單世界 5,000 的測試，非每世界自動保證 5,000。
- 實體主機與部署環境尚未指定，先做可在本機啟動的多程序配置，再選定容量測試硬體。
- 進度 RPO 10 秒、世界 RTO 60 秒與 P99 延遲是初始提案；資產成功提交的完整性是必要條件。
- 商城／世界單次交接憑證與腳本 VM 的相容 PoC 在 P0 完成，避免核心寫完才發現客戶端／腳本限制。

不以未通過的容量、故障或內容案例標記對應需求完成。
